# ADR-007: Function access to the telemetry stream

## Status

Accepted

## Context

The Azure Function consumes device telemetry from IoT Hub. How it authenticates to that
stream is a security decision, and it has to be made before the infrastructure is written
(#2), because the templates differ completely between the options.

The preferred answer would be a managed identity: no secret to store, rotate or leak.
Microsoft's documentation rules that out for IoT Hub's built-in endpoint, in two places:

- IoT Hub's Entra ID documentation: *"To get data from IoT Hub by using Microsoft Entra ID,
  set up routing to a custom Event Hubs endpoint. To access the built-in Event Hubs
  compatible endpoint, use the connection string (shared access key) method as before."*
- The Azure Functions IoT Hub trigger documentation: *"The IoT Hub trigger doesn't support
  identity-based connections. If you need to use managed identities end-to-end, you can
  instead use IoT Hub Routing to send data to an event hub you control."*

A connection string requires a shared access policy with the `ServiceConnect` permission,
and that permission is broader than reading telemetry: it also allows sending
cloud-to-device messages and updating device twins.

## Options

1. **Built-in endpoint, connection string in Key Vault.** The Function reads the built-in
   endpoint. The connection string is generated by the deployment and stored in Key Vault;
   the Function reads it through a Key Vault reference, using its managed identity.
2. **Custom Event Hubs endpoint, managed identity end to end.** IoT Hub routes telemetry to
   an Event Hubs namespace with its own managed identity (`Azure Event Hubs Data Sender`),
   and the Function reads it with its managed identity (`Azure Event Hubs Data Receiver`).
   No secret anywhere in the pipeline.
3. **Built-in endpoint, connection string as a plain app setting.** The simplest, but it puts
   the key in the app's configuration rather than in Key Vault, against the project's rule
   that secrets live in Key Vault.

## Decision

**Option 1.**

- A dedicated shared access policy holds only `ServiceConnect`, so the Function's key can be
  rotated or revoked without affecting anything else that talks to the hub.
- The Bicep template reads that policy's key with `listKeys()` at deployment time, builds the
  Event Hubs-compatible connection string and writes it straight into a Key Vault secret. No
  person handles the key, and it never appears in the repository, a parameter file or a
  deployment output.
- The Function App setting `IoTHubConnection` is a Key Vault reference, resolved with the
  Function's managed identity, which holds `Key Vault Secrets User` on that vault only.
- The connection string carries the endpoint's Event Hubs-compatible name as `EntityPath`.
  Per the trigger documentation, a name in the connection string overrides the trigger
  attribute's event hub name at runtime, so `TelemetryFunction` needs no change.

Option 2 is the stronger design, and it was not rejected on technical grounds. It costs
money continuously: the Event Hubs Basic tier bills per hour whether or not anything flows —
US$0.015 an hour in West Europe, about US$11 a month — which is most of the project's
budget. It also adds a resource to the architecture and uses the free IoT Hub tier's only
custom endpoint.

Option 3 was rejected outright: it saves nothing over option 1 except the Key Vault
reference, and gives up the one place where the secret is controlled and audited.

## Consequences

- **One long-lived secret remains.** It is generated and stored by the deployment, scoped to
  a dedicated policy and readable only by the Function's identity, but it does not expire.
  Rotation means regenerating the policy key and redeploying; it is not automated.
- **`ServiceConnect` is broader than the Function needs.** A leaked key could send
  cloud-to-device messages and update device twins, not just read telemetry. That weighs
  more once cloud-to-device configuration exists (#16), and is an explicit item for the
  security review (#21).
- **IoT Hub keeps hub-level SAS enabled.** Disabling local authentication on the hub would
  break the Function's connection.
- **The upgrade path to option 2 is contained.** It changes infrastructure (an Event Hubs
  namespace, a route, two role assignments) and the trigger's connection setting, but not
  the processing code: `TelemetryService` receives the payload and the authenticated device
  identity from the transport, and does not care which endpoint delivered them. Whether
  messages routed to a custom endpoint carry `iothub-connection-device-id` the same way would
  need confirming at that point, since the trust model depends on it.
- **Routing (#9) targets the built-in endpoint.** Once any route exists, the built-in
  endpoint only receives messages that a route sends there explicitly, or that fall through
  to the fallback route.
- **To be verified in #2:** that Flex Consumption resolves a Key Vault reference used as a
  trigger's connection setting, since the platform's scaler reads that setting too.
